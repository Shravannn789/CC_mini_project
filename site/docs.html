How Cloud Block Vault works

From segmentation to edge delivery: the architecture, every operation, the cryptographic design, and how to host this site on Amazon S3 behind CloudFront with HTTPS.

Architecture

A file never leaves the machine whole. It is streamed into fixed-size segments, each segment is encrypted independently, and the resulting ciphertext blocks plus a small JSON manifest are written to object storage. The manifest is written last, so its presence marks a completed upload.

Operations

CommandWhat it does
split <file>Divides a file into fixed-size segments in a local folder (blocks/000000.blk, …) plus segments.json with per-block checksums.
merge <segDir>Reassembles segments and verifies size + SHA-256 against the metadata.
upload <file>Split → encrypt each block → upload blocks and manifest to the store (local or s3).
download <id>Fetch manifest + blocks, verify checksums, decrypt, reassemble, and verify the final SHA-256.
download <id> --keep-encryptedDownloads the ciphertext exactly as stored in the cloud (blocks + manifest) without decrypting.
restore <encDir>Decrypts a vault that was downloaded in encrypted form, back into the original file.
list / verifyList vaults in the store; verify stored checksums (and GCM authentication when a passphrase is given).

Storage backends

The storage layer is a tiny abstraction — putObject, getObject, listObjects, deleteObject — with two implementations:

  • local (default): the same semantics on the filesystem under .store/, so the entire workflow runs offline and in tests.
  • s3: the S3 REST API signed with AWS Signature Version 4 implemented from the specification (no SDK). Works with AWS S3 and S3-compatible endpoints (MinIO, Ceph, R2) via --endpoint.
Verified against AWS's own example. The signing code reproduces the exact signature published in the AWS S3 SigV4 documentation worked example (f0e8bdb8…36bdb41), which is asserted in the test suite. 
export CBV_BUCKET=my-vault-bucket
export CBV_REGION=us-east-1
export CBV_PREFIX=demo            # optional key prefix inside the bucket
export AWS_ACCESS_KEY_ID=...
export AWS_SECRET_ACCESS_KEY=...
export CBV_PASSPHRASE=...
node src/cli.js upload bigfile.bin --backend s3
node src/cli.js list --backend s3
node src/cli.js download bigfile.bin-20261020T120000 -o restored.bin --backend s3

Security model

  • Key derivation — the passphrase is never used directly; scrypt (N=16384, r=8, p=1) with a random 16-byte salt from the manifest derives a 256-bit key.
  • Per-block AES-256-GCM — every block uses a fresh 12-byte random nonce; the 16-byte auth tag detects any modification of the ciphertext.
  • Block binding (AAD) — the vault id and block index are fed into GCM as additional authenticated data, so blocks cannot be reordered, duplicated, or replayed from another vault.
  • Checksums — the manifest stores a SHA-256 per stored block and for the whole plaintext file, catching corruption before decryption and after reassembly.
  • Secrets hygiene — the passphrase and AWS keys come from flags/environment, never from the manifest; the manifest and salt are public by design.

Hosting the site: S3 + CloudFront + HTTPS

This site is static HTML/CSS, which is exactly what object storage + a CDN are for. infra/deploy-site.sh provisions the whole path:

  1. Create a private S3 bucket and block all public access.
  2. Sync the site/ folder into the bucket.
  3. Create a CloudFront distribution with Origin Access Control (OAC), so users can only reach the files through the CDN.
  4. Attach a bucket policy that allows only that distribution to read objects.
  5. Force HTTP → HTTPS redirection and set index.html as the default root object.
export AWS_REGION=us-east-1
export SITE_BUCKET=my-portfolio-site-12345   # globally unique
./infra/deploy-site.sh                       # prints the https://dxxxx.cloudfront.net URL

Why a CDN?

  • Latency — CloudFront caches content at edge locations close to visitors; a fetch that would cross the ocean once is now served from the nearest region.
  • HTTPS everywhere — CloudFront terminates TLS with a default certificate for its domain (or your own via ACM/IAM), and the distribution can redirect plain-HTTP requests, so encryption in transit is enforced end to end.
  • Origin protection — with OAC the S3 bucket stays fully private; only the CDN can read it.
  • Invalidation — after re-uploading files, aws cloudfront create-invalidation (see infra/invalidate.sh) pushes fresh content to every edge.
